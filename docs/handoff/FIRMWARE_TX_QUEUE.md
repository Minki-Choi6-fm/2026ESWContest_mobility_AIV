# FIRMWARE_TX_QUEUE — "STM32 TX 링버퍼가 차서 프레임이 버려진다" 가설 (코드 확인 + 로그 확인, 펌웨어는 수정하지 않음)

대상: STM32 담당(최민기)과 Pi5 쪽 분석 담당. 근거 파일: `firmware/stm32_rear/main_v18c.c` (86,602 B, 10/24 12:49), 분석 도구 `pi5/pipeline/tx_queue_analysis.py`.
`[가설]` = 측정으로 증명되지 않은 해석.

## 1. 코드에서 확인한 사실 (main_v18c.c)
| 항목 | 내용 | 위치 |
|---|---|---|
| TX 링버퍼 | `tx_buf[512]`, 사용 가능 511 B | `TX_BUF_SIZE`, `proto_send()` |
| 가득 차면 | `freesp < total` 이면 그 프레임을 **버리고** `tx_drop_count++` 후 0 반환. 재시도 없음 | `proto_send()` (≈1352–1358) |
| **tx_drop_count 노출 여부** | 선언(1307)과 증가(1356)뿐. **디버그 출력(RADSTAT 등)이나 0x11 하트비트에 나가지 않음** → 지금 로그로는 직접 관측 불가 | `grep tx_drop_count` = 3곳 |
| RADSTAT 의 `drop=` | 이것은 `dbg_drop_count`(디버그 **텍스트** 출력 유실)이지 tx_drop_count가 아님. 혼동 주의 | 693–699 |
| 전송 방식 | `HAL_UART_Transmit_IT` 로 연속된 한 덩어리(chunk)씩 보냄. **`tx_tail` 은 chunk 전체가 끝나야 이동** (`HAL_UART_TxCpltCallback`). 즉 전송 중인 chunk 전체가 "사용 중"으로 계산됨 | `uart_tx_kick()`, 1413–1419 |
| 0x10 | `if (now - t_sum >= 20) { t_sum = now; ... proto_send }` — 위상 고정 아님(지터 21–24 ms의 이유). **proto_send 가 버려도 다음 0x10 은 20 ms 뒤** → 수신 측에서는 **정확히 40/60 ms 간격**으로 보임 | `proto_task()` |
| 0x12 | 물체마다 `radar_publish()` → `proto_send()` 한 번(19 B). `rad_npub++` 가 호출 **직전**에 증가 → RADSTAT `pub` = 큐에 넣으려 한 0x12 수 | 639, 656 |
| 프레임 크기(전선 위) | 0x10 16 B, 0x11 11 B, 0x12 19 B, 0x13 28 B, 0x14 10 B | `len+5` |
| 선로 용량 | 115200 8N1 = 11,520 B/s = 11.52 B/ms. 512 B 링은 최대 약 44 ms 분량 | |

## 2. 실측과 비교
- 실측 평균 부하: 0x10 50 Hz×16 + 0x11 10 Hz×11 + 0x13 20 Hz×28 + 0x14 ≈3 Hz×10 + 0x12 ≈223/s×19 = **≈5.7 kB/s ≈ 선로의 50 %** (사용자 값과 일치).
- 레이더 한 사이클에서 **연속으로 큐에 들어가는 최대 바이트**(로그 3개, 같은 STM32 ts로 묶음): 객체 최대 **22–24개 → 최대 418–456 B**, 평균 6.2개(≈118 B), p95 15–16개(≈290 B).
  → 빈 링이라면 한 사이클 폭발만으로는 넘치지 않지만(511 B 한도 = 26개), **0x10/0x13/0x11 이 같이 들어가고 전송 중 chunk 가 통째로 점유로 계산되면** 쉽게 한계에 닿음.
- **확인 1 (직접 비교)** `pub`(RADSTAT) 대비 Pi5가 받은 0x12 (1초 창 단위, 리셋 구간은 epoch 분리):

| 로그 | 창 | 발행(pub) | 수신 | 부족 | 부족 비율 |
|---|---|---|---|---|---|
| 141541 | 1601 | 290,712 | 281,412 | 9,300 | **3.20 %** |
| 151202 | 595 | 135,181 | 129,531 | 5,650 | **4.18 %** |
| 152211 | 424 | 97,328 | 94,144 | 3,184 | **3.27 %** |

  → 0x12 는 3–4 % 사라짐. 0x10/0x11 손실 1.3–2.3 % 보다 약 2배 → 큰 프레임(19 B)이 더 잘 버려지고 폭발적으로 들어오는 0x12 가 더 많이 걸리는 모습과 일치 (균일한 비트 오류라면 크기 비례 ≈1.2배).
  단, "사라짐"에는 큐 폐기 외에 Pi5 로거가 걸러낸 오류 프레임도 포함됨.
- **확인 2 (링 모델)** 펌웨어와 같은 규칙(511 B, chunk 단위 해제, 11.52 B/ms)으로 **수신된 프레임들의 STM32 타임스탬프**를 먹여 "빠진 0x10 슬롯" 직전의 사용량을 계산:

| 로그 | 빠진 슬롯의 사용량 중앙값 | 사용량 > 495 B (16 B 프레임이 버려질 조건) | 정상 슬롯에서 같은 조건 |
|---|---|---|---|
| 141541 | 503 B | 673/1054 (**64 %**) | 4/15000 (0.0 %) |
| 151202 | 503 B | 419/696 (**60 %**) | 83/22418 (0.4 %) |
| 152211 | 503 B | 206/364 (**57 %**) | 40/15000 (0.3 %) |

  모델은 "수신된(=받아들여진) 프레임만" 넣으므로 실제 점유보다 낮게 계산될 수 있고, 반대로 chunk 재시작 지연 등을 무시해 약간 비관적일 수도 있음(펌웨어가 받아들인 프레임 중 모델이 못 넣은 것: 로그당 153–424개, 전체의 0.1 % 미만).
- **해석 [가설, 두 개의 독립적인 확인이 일치]**: 빠진 0x10 의 대부분(57–64 % + 사용량 가까이 간 것 77–81 %)이 TX 큐 폐기와 일치한다. 증명은 아님 — `tx_drop_count` 값을 직접 보아야 확정.

- **확인 3 (S6, 선로 용량)** RADSTAT `pub`(초당 큐에 넣으려 한 0x12 수)를 초 단위 부하로 환산: 0x12 한 개 = 19 B이고 0x10/0x11/0x13/0x14 가 평소 약 1,500 B/s 이므로, 115200 baud(11,520 B/s)가 0x12 를 **최대 약 527개/초**까지만 실을 수 있음.

| 로그 | 평균 pub | p95 | 최대 | 용량 초과 초 | 그 초들에 든 0x12 손실 비중 | 그 초들의 0x12 도착률 |
|---|---|---|---|---|---|---|
| 141541 | 182/s | 457 | 777 | 46/1601 (2.9 %) | **67 %** (6,271/9,300) | 76 % |
| 151202 | 227/s | 497 | 773 | 22/595 (3.7 %) | **70 %** (3,934/5,650) | 71 % |
| 152211 | 230/s | 466 | 745 | 15/424 (3.5 %) | **84 %** (2,685/3,184) | 71 % |

  예: 152211 의 STM32 시계 218–220 s 구간은 RADSTAT 에서 `b`(받은 0x60B)=741–860/s, `pub`=620–745/s → 0x12 만 11.8–14.2 kB/s + 기타 1.5 kB/s = **약 13–16 kB/s 로 선로 용량(11.52 kB/s)을 넘음.** 이런 초에서는 링 크기와 상관없이 드롭이 **물리적으로 불가피**.
  → 0x12 손실의 약 2/3–5/6 은 "레이더가 선로가 감당 못 할 만큼 객체를 쏟아내는 초"에서 발생. 나머지(16–33 %)는 평소 부하에서의 chunk 회계/기타(확인 2).
  이 결과는 옵션 3(한 사이클 객체 수 제한)과 5(보레이트 상향)의 근거를 크게 강화함. 링 확대(옵션 2)나 chunk 제한(옵션 1)만으로는 **지속 과부하 초는 해결되지 않음**(지연만 늘거나 드롭이 늦게 일어남).

- **확인 4 (S7, 필터가 꺼져 있음 + CAN 단계 손실)** `main_v16.c`, `main_v17.c`, `main_v18c.c` 모두 **`#define TEST_ALL_CLASSES 1`** (66행) → 차량 클래스(`objClass==1`) 필터가 **꺼져 있어** 점형체(기둥·펜스·사람)까지 UART 로 나감. RADSTAT 로 측정: `pub`(UART 로 보낸 수) / `veh`(차량 클래스 수) = **4.7 / 2.8 / 3.6 배** (141541 / 151202 / 152211: pub 291,018 vs veh 61,602; 135,356 vs 48,579; 97,852 vs 27,032).
  → 필터를 켜면(`TEST_ALL_CLASSES 0`) 0x12 부하가 약 1/3–1/5 로 줄어 **선로 과부하 초가 사라짐**(§2 확인 3). 단 Pi5 는 점형체/가드레일을 더 이상 못 보고 레이더의 차량 분류(objClass)에 의존하게 됨(분류가 틀리면 실제 차량도 사라질 수 있음 [가설]); `PROTOCOLS.md` 의 "차량 클래스만 통과" 서술은 **시험 빌드에서는 사실이 아님**.
  또한 같은 로그의 RADSTAT 에서 **MCP2515 수신 버퍼 넘침(`ovf` 증가)이 객체가 많은 초(`b` ≥ 500/s)에 거의 항상 동반**: 222/223, 93/95, 51/51초. 레이더가 알린 객체(`exp`) 대비 STM32 가 받은 객체(`b`) 부족은 5.3 / 4.9 / 3.5 % → **손실은 UART 링 이전, CAN 수신 단계에서도 발생**(객체 많은 초에 7–9 %). `TEST_ALL_CLASSES` 와 무관하게 CAN 쪽 폴링/인터럽트 처리 한계(RX 버퍼 2개)를 의미 [가설].

## 3. 다음 주행에서 확인하는 법 (펌웨어 수정 없이)
1. 수신기(`live_receiver.py`/`pipeline_main.py`)의 `loss_pct`·`BAD`: **BAD=0 인데 loss>0** 이면 비트 오류가 아니라 STM32 쪽 누락(또는 수신 지연)이라는 뜻.
2. 주행 후 `python3 -I pi5/pipeline/tx_queue_analysis.py <drive>` → ① pub 대비 수신 0x12 부족 비율 ② 빠진 슬롯의 링 사용량 분포. (stm_debug.log 의 RADSTAT 필요 → `drive_logger_nouart` 가 ttyACM0 을 기록해야 함.)
3. 레이더 객체가 많은 장소(차량 많은 길)와 적은 장소에서 비교: 객체 수/사이클이 많을수록 손실이 늘면 지지.

## 5. 펌웨어 수정안 파일 (S6-d, 적용 금지 — 빌드/플래시 안 함)
- `firmware/stm32_rear/main_v18c.c` **는 수정하지 않았음** (Downloads 사본과 동일, sha256 앞 16자 `11c720968228dc50`).
- 복사본 `firmware/stm32_rear/main_v18d_proposed.c` 와 `main_v18c_to_v18d.diff`: **변경은 하나** — `tx_drop_count` 를 기존 RADSTAT 디버그 줄(USART2 = ST-Link VCP)의 `drop=` 옆에 `txdrop=` 로 출력.
  실제 diff 는 3줄: ① `extern volatile uint32_t tx_drop_count;` (RADSTAT 출력 위치가 정의(1307행)보다 앞이라 선언 필요, `dbg_drop_count` 와 같은 방식) ② 포맷 문자열에 `txdrop=%lu` ③ 인자 `(unsigned long)tx_drop_count`.
  동작 변경 없음(읽기만, 제어 흐름/타이밍/프로토콜 불변). 펌웨어 배너(`FW v18c ...`)는 그대로 둠 — 버전 표기를 바꿀지는 팀 결정.
- **sprintf 버퍼 확인(코드로):** RADSTAT 는 `char rs[256]` 에 `sprintf`. 형식의 고정 문자 85자(CRLF 포함) + `%lu` 14개 + `%u` 2개. 모든 필드가 10자리라고 가정한 **이론상 최악 245자 (+NUL 246) ≤ 256 → 오버런 없음** (기존 줄은 최악 227자). 실제 값은 훨씬 작음(`tec/rec` 는 0–255 → 3자리, 카운터 대부분 5–6자리 → 약 170자). 여유는 약 10 B 이므로 **이 줄에 필드를 더 추가하면 `snprintf(rs, sizeof rs, ...)` 로 바꾸거나 버퍼를 늘릴 것.**
  디버그 TX 링은 1024 B(`DBG_BUF_SIZE`)라 1초에 한 줄(≈170 B)은 문제 없음.
- **문법 확인:** `arm-none-eabi-gcc` 는 이 Pi5 에 없음 → 호스트 `gcc -fsyntax-only`(HAL/CMSIS 헤더 경로 지정, newlib `_ansi.h` 는 스크래치에 빈 스텁)로 v18c / v18d_proposed 를 각각 검사: **둘 다 오류 0, `-Wformat` 경고 수 동일(3, 기존)**. 이것은 ARM 빌드가 아니므로 실제 빌드(CubeIDE)에서 한 번 더 확인해야 함. `.bin`/`.o` 는 만들지 않음.
- 로그 도구: `loss_analysis.py <drive> --txdrop` 가 `stm_debug.log` 의 RADSTAT 에 `txdrop=` 가 있으면 **초당 증가량**을 같은 초의 Pi5 손실(빠진 0x10, `pub`-수신 0x12)과 맞춰 상관·일치 초 수·최악 초를 출력. 없으면 "skipped (firmware before v18d)" 로 무시. (`--selftest`: 합성 열로 연결만 시험 — 데이터 아님.) 판독: txdrop > Pi5가 본 손실 = Pi5가 못 본 프레임이 버려짐, txdrop < 손실 = 비트 오류/로거 등 다른 손실.
