# PROJECT_STATE — AIV V2V safe-distance warning (rear car)

Snapshot of knowledge up to ~2026-10-24. Verify against the real Pi5 (`tools/snapshot_pi5.sh`).

## 1. Goal
Mutual safe-distance warning between a commercial truck (rear) and a passenger car (front)
using V2V. Competition: 제24회 임베디드SW경진대회 (자동차/모빌리티), finalist stage.
Final deliverables: development report (PDF, ≤20 body pages + cover/thanks), source code
(GitHub) and demo video (YouTube) links are mandatory. Online presentation 5–7 min, purpose is expert consulting.

Dynamic safe distance (design doc): `d = v² / (2·K·g) + v·t`, K = effective braking coefficient
(IMU-based estimate, valid range 0.3–1.0), t = reaction time. K/t values: ❓ not finalized.

## 2. Architecture (dual processor)
```
Rear car
  MR76 radar --CAN--> MCP2515 (SPI2) --> STM32 NUCLEO-F446RE --UART1 115200--> Pi5 (/dev/ttyAMA2)
  IMU (UART3), OBD module (UART6, Longan Serial CAN), OLED SSD1306 (I2C2), buzzer (user integrating)
  Pi5: RealSense D435i (color only) + YOLOv8n, GPS (gpsd, /dev/ttyAMA0), V2V node, loggers
Front car (separate): RPi4 + STM32 + OLED (display warning); no radar/camera
Side "virtual car": RPi4 broadcasting BSM only (demo of multi-vehicle target selection)
V2V: BSM 26 bytes, CRC-16, 10 Hz, UDP broadcast (tested locally) / ESP32 ESP-NOW (2 ESP32 test succeeded)
```
- Layering (AUTOSAR-like): STM32 = safety/real-time; Pi5 = AI inference + V2V + target selection.
- STM32 firmware is a **bare-metal HAL main loop** (no FreeRTOS found in main_v15–v18c),
  although older notes say "FreeRTOS". Treat "FreeRTOS" as inaccurate unless you find it in the code.
- Danger decision: in firmware `K_VALUE=0xFF` and `DANGER_FLAG=0xFF` (not implemented in STM32,
  main_v18c.c ~line 1558–1561). So the real danger logic is NOT finished anywhere unless a
  teammate added it — ❓ check Pi5 code.
- Pi5 → STM32 downlink: 0x22 EGO_SPEED (GPS speed fallback) implemented; 0x20/0x21 warning/link-status: ❓ check.

11. **GPS speed lags OBD by ≈ 1.0–1.4 s** ✅ (best time-shift in 3 runs); MAE OBD-vs-GPS ≈ 1.6–1.9 km/h unshifted, ≈ 0.9–1.0 shifted (max 15.5).
    Matters for BSM/ego-speed on the front car, which has GPS only. Cause (gpsd/NMEA 1 Hz/module filtering) is a hypothesis.

12. **Unread UART data piles up in the kernel** ✅ measured 2026-10-24 on `/dev/ttyAMA2`: the first read of `live_receiver.py` returned
    ≈1.3 MB (measured). Dividing by ≈1.47 kB/s gives ≈ 15 min of traffic (a conversion; whether the kernel really keeps that much is unconfirmed). A third read (~1 h later) again returned ≈ 1.31 MB, so the kernel seems to keep a FIXED maximum (≈1.3 MB), not "everything since the last read" [hypothesis from two equal readings]. A second start after ≈ 1 min returned ≈ 29 kB (measured). So a reader that starts late sees OLD frames
    stamped with the read time. Every reader must discard the backlog at start (`live_receiver.py` does and records the size) and, in the car,
    exactly one process must read the port (a second reader would split the bytes and break frames).
13. **0x14 OBD_DATA cadence when the OBD module does not answer ≈ one frame per 3 s, `SPEED=0xFF`** ✅ measured (desk, 30 s: 10 frames);
    with a working OBD it was ≈ 3 Hz in the 10-16 drives. So a 100 ms frame timeout can never apply to 0x14; the 1000 ms proposal
    (`pi5/pipeline/constants.py`) already reads "stale" most of the time while OBD is silent. Behaviour after an OBD failure *with* a known last speed
    (last value + growing AGE_MS, per main_v18c.c as told by the user) is **not yet seen in a real log** — verify when a drive with OBD loss exists.
    RPM is always 0xFFFF (not implemented).
14. **Desk-setup test environment (2026-10-24)**: only the STM32 connected to the Pi5 — no radar, OBD module or GPS fix (gpsd `mode 1`).
    Seen: 0x10 50 Hz, 0x11 10 Hz, 0x13 20 Hz all stable, BAD frames 0 over 44,347 bytes (30 s); 0x12 = 0 frames; `speed=NONE`.
    Radar (0x12) is only sent when objects exist [hypothesis: RADAR_OK in SENSOR_STATUS of 0x10, not 0x12 presence, is the right "radar alive" signal].

15. **Radar: alive vs target** ✅ (desk, real `/dev/ttyAMA2`, 30 s read-only; radar connected, boxed, no object in view): all 1503 `0x10` frames had
    SENSOR_STATUS = **0x0B** = RADAR_OK 1, IMU_OK 1, OBD_OK 0 (no OBD module), CAN_OK 1, SAFE_MODE 0, BRAKE 0, and **0 frames of 0x12**.
    So "no 0x12" ≠ "radar dead". In `pi5/pipeline/uart_ingest.py`: `radar_alive()` = RADAR_OK bit of a valid 0x10; `radar_has_target()` = 0x12 seen
    within 100 ms; `is_valid("radar")` keeps meaning "0x12 recently seen" (= target present), NOT health. Decision logic must use radar_alive() for health.
16. **Frame loss from the STM32 clock** (`live_receiver.py`, `loss_pct`; method validated: injected 22+3 corrupted 0x10/0x11 frames + 4+3 natural gaps = 26+6 measured, exact):

17. **V2V (9/27 code) rejects a restarted sender** ✅ measured in software loopback (`loopback_v2v_test.py` S7): after the rear node restarted with SEQ 300→0,
    the front node's `FreshnessTracker.update()` dropped ALL 76 frames of the next 8 s as "DUP" and the rear stayed STALE (no LIVE event), because it compares
    SEQ with the stored last_seq even when that entry is already STALE. It recovers only when the new SEQ passes the old one (≈ old_seq/10 s at 10 Hz). Not changed
    (V2V code read-only; owner 최민준). Suggested: accept any frame, resetting last_seq, when the stored entry is STALE.
18. V2V STATUS bits: the 9/27 `bsm_protocol.py` defines only bits 0-3 (GPS_VALID, DANGER_ACTIVE, SENSOR_DEGRADED, SAFE_MODE). Bits 4-6 (BRAKE_ACTIVE, SPEED_SRC_GPS, SPEED_STALE) are
    [PROPOSAL] only; `v2v_adapter.py` ORs them into the byte and recomputes the CRC. Receivers on the original code ignore them. `255.255.255.255:9000` leaves through wlan0 —
    tests use `127.255.255.255:19000`.
