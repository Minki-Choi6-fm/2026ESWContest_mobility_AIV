# SERIAL_WRITE_OPTIONS — Pi5 → STM32 쓰기 주체 정리 (정리만, 코드/서비스 변경 없음)

배경: `/dev/ttyAMA2` 의 **쓰기**는 지금 `aiv-ego-speed` 서비스(`ego_speed_tx.py`, 0x22 EGO_SPEED, 5 Hz, GPS만)가 맡습니다. 통합 실행 파일(수신기/노드)은
읽기 전용입니다. 이후 0x20 DISPLAY_WARNING(LEN 4)과 0x21 LINK_STATUS(LEN 1)까지 보내려면 누가 쓸지 정해야 합니다. 읽기 쪽 문제
("프로그램이 둘이면 바이트가 나뉜다")와 별개로 **쓰기는 프레임이 섞일 위험**이 문제입니다.

공통 제약(규칙 2): STM32 안전 루프는 Pi5 에 의존하면 안 됩니다. 어떤 방식이든 0x20/0x21/0x22 가 안 와도(타임아웃) STM32 는 로컬 레이더 경고를 계속해야 합니다.

## 참고 측정 (이번 작업에서)
- `ego_speed_tx.py` 는 포트를 `timeout=0, write_timeout=0.2` 로 열고 **프레임 1개(10바이트)를 `write()` 한 번에** 씁니다. 읽기는 하지 않습니다. `flock`/`exclusive` 없음.
- **가상 pty 실험(실제 UART 아님):** 두 프로세스가 각각 한 번의 `write()` 로 프레임(10 B / 9 B)을 4만 개씩 동시에 쓰고 한쪽이 읽었더니
  **8만 프레임 모두 온전, 재동기화 0회.** 즉 "write 한 번 = 한 덩어리" 로 취급될 수 있음을 시사하지만, 실제 UART(전송 버퍼가 차서 부분 쓰기가 생길 수 있는 경우)에서는
  **검증하지 않았습니다 [가설]**. 5–10 Hz 의 작은 프레임에서는 버퍼가 찰 일이 거의 없다는 점이 근거일 뿐입니다.

## 옵션
| | 방식 | 장점 | 단점 / 위험 |
|---|---|---|---|
| A | 서비스가 계속 유일한 쓰기 주체, 통합 프로그램은 서비스에 요청만 전달(소켓/파일) | 쓰기 한 곳, 프레임 안 섞임 | **서비스(ego_speed_tx.py) 수정 필요** — 현재 금지. 서비스 재시작/장애 시 모든 다운링크 영향 |
| B | 통합 프로그램이 0x22 까지 흡수, 서비스는 정지/비활성 | 쓰기 한 곳, `get_speed()`(OBD 우선) 로 0x22 의 SOURCE 를 정확히 보낼 수 있음(지금 서비스는 GPS 전용), 프레임 스케줄 일원화 | 서비스 변경(승인 필요). 통합 프로그램이 죽으면 0x22 도 끊김 → STM32 는 0x22 타임아웃 처리 필요(규칙 2/5). 부팅 순서/자동 재시작(systemd) 새로 설계 |
| C | 서비스(0x22)와 통합 프로그램(0x20/0x21)이 **동시에** 같은 포트에 씀 | 서비스/설정 변경 없음, 가장 빠름 | write 원자성에 의존 [가설: pty 에서만 확인]. 두 쓰기 주체의 전송률 조율 불가(STM32 파서 입장에서 순서 없음). 문제 생기면 원인 추적 어려움. STM32 가 프레임 파싱 실패 시 재동기화(LEN 고정, 즉시 폐기) 하는지는 펌웨어에서 확인 필요 |
| D | **포트 프록시/멀티플렉서**: 작은 전용 프로세스가 `/dev/ttyAMA2` 를 단독 소유하고, 읽은 바이트를 여러 소비자에게 나눠 주고(팬아웃), 여러 송신자의 프레임을 순서대로 한 줄로 써 줌(pty 또는 유닉스 소켓) | **읽기·쓰기 문제를 한 번에 해결**(로거/분석 도구도 포트를 못 건드려도 됨), 프레임 단위 직렬화 | 새 프로세스 1개 추가(지연 수 ms, 장애 지점). 서비스는 그 소켓으로 보내도록 바뀌어야 완전해짐(또는 C 와 병행). 구현/시험 시간 필요 |
| E | 다운링크용 **별도 UART**(STM32 USART 하나 더 + 배선) | 읽기/쓰기 완전 분리 | 펌웨어·배선 변경 필요 — 지금 단계에서 비현실적 |

## 권고 (의견이며 결정은 팀)
1. **첫 주행 시험:** 쓰기 변경 없음. 서비스가 0x22 만 쓰고, 통합 프로그램은 읽기 전용(0x20/0x21 안 보냄).
2. 0x20/0x21 이 실제로 필요해지는 시점(전방차 OLED/부저 경로 시험)에 **D(프록시)** 를 우선 검토하되, 급하면 **C** 를 실제 UART 에서 짧게 검증한 뒤 임시로 사용.
3. B 는 OBD 우선 속도(규칙 4/12)를 STM32 로 보내는 쪽으로 가는 최종 형태로는 자연스럽지만 서비스 변경과 STM32 타임아웃 확인이 선행돼야 함.

## 결정이 필요한 질문
- 0x20/0x21 송신을 언제까지 구현할지(전방차 경로 시험 일정)? 누가 STM32 쪽 수신(타임아웃/재동기화)을 확인하는지?
- 서비스 수정/비활성화를 허용하는지(A/B)? 아니면 C 를 실기에서 먼저 검증할지?
- STM32 가 0x22 의 `SOURCE=0xFF, AGE=65535`(GPS 끊김)를 어떻게 처리하는지 펌웨어 확인 담당자는?
