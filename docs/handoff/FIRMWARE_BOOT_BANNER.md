# 부팅 배너 유실 조사 (S9-c) — 소스·바이너리·기존 로그만 읽음, 보드 접속/새 캡처 없음

관찰: `logs/ttyACM0_capture_20261025_reset.txt` 에서 `RESET CAUSE`, `FW v18…`, `BOOT1` 이 없고 `…SAFE MODE t=3202220BOOT2` 로 바로 이어짐.

## 1. dbg_tx 구현과 `Timeout=0` (사실)
- `dbg_tx(p, len, unused)` (main_v18c.c:1390): 세 번째 인자는 **사용 안 함**. `HAL_UART_Transmit` 을 호출하지 않고, 1024 B 링버퍼에 복사 후 `dbg_kick()` → `HAL_UART_Transmit_IT(&huart2, …)`. 완료 콜백(`HAL_UART_TxCpltCallback`)이 이어서 보냄. v17(old/main_v17.c:1256)도 같은 구조.
- 따라서 `RESET CAUSE`/`FW`(인자 0)와 `BOOT1`(인자 100)은 **완전히 같은 경로**. "타임아웃 0 이라 일부만 나감"은 **이 코드에는 해당 없음**. (참고: 실제 `HAL_UART_Transmit(…, 0)` 이었다면 `UART_WaitOnFlagUntilTimeout` 가 `Timeout==0` 이면 플래그가 안 서 있을 때 즉시 HAL_TIMEOUT → 일부만 전송될 수 있음. 이 파일에서 `HAL_UART_Transmit` 은 huart6(OBD) 3곳, 타임아웃 200 뿐.)
- 버퍼 상태: 리셋 직후 링은 비어 있고(`freesp` 충분) 세 줄 합계 ≈70 B → 115200 baud 로 약 6 ms 면 송출 완료. HAL_Delay(2000) 중에도 USART2 인터럽트(우선순위 7)가 동작하므로 **펌웨어 쪽에서 버려질 이유는 코드상 찾지 못함**. 초기화 순서도 `MX_USART2_UART_Init()` → NVIC 활성 → 출력 순이라 정상. (실제 보드 동작은 확인 못 함.)
- 한계: 이 판단은 소스 읽기이며 v18c 바이너리로 실행해 본 것이 아님. 보드가 정말 v18c 인지도 "사용자 육안 확인, 배너 미확인".

## 2. BOOT1 도 없는 이유 — 가설 (증거 강도 순)
| # | 가설 | 근거 | 반대 근거 / 한계 |
|---|---|---|---|
| H1 | **캡처 시작 시각**: 사용자가 "지금 리셋 누른다" 후 명령이 실행됨. BOOT2 가 캡처 0.12 s 에 나왔고 BOOT2 는 리셋 후 ≈2 s 이므로 **리셋은 캡처 시작 약 1.9 s 전**. 배너 3줄(리셋 후 수 ms)은 포트를 열기 전에 나갔음 | 타임라인 계산, 이전 줄이 `t=3202220` 에서 끊김 | 포트가 닫혀 있던 동안 바이트가 어디에 남는지는 아래 H2 에 달림 |
| H2 | **포트 닫힘 중 유실**: 읽는 프로세스가 없을 때 ST-Link VCP/USB 단의 작은 버퍼가 가득 차거나, 열기 직전 `cdc-acm` 이 앞 바이트를 버림 | 리셋 전 2.4 s 분량(`t=3199868…3202220`)은 한꺼번에 0.00 s 에 읽혀 **열기 전부터 어딘가에 쌓여 있었음** | 쌓인 구간이 "리셋 직전까지"인데 직후 70 B 만 빠진 것은 설명이 약함 → [가설] 리셋 때 ST-Link 가 VCP 를 재동기화하며 비움 |
| H3 | 리셋 순간 ST-Link 브리지 재동기화로 첫 수 ms 가 유실 | 이전 줄이 CRLF 없이 끊김 | 10/16 151202 로그(연속 읽기 중)는 리셋 후 `RESET CAUSE: other/pin` 과 `BOOT1` 이 **찍혔음**(펌웨어는 v17 계열, 같은 dbg_tx 구조) → 연속 읽기 중이면 보통 유실 안 됨 → H1/H2(읽는 쪽 부재) 쪽에 무게 |
| H4 | 펌웨어에서 `dbg_tx` 가 가득 참으로 버림 | `dbg_drop_count` 존재 | 리셋 직후 링이 비어 해당 없음(코드상) |
| H5 | 배너 코드 자체가 실행 안 됨(다른 펌웨어) | — | `BOOT2`, I2C 스캔, `OLEDSTAT` 형식이 v18b 이후와 일치. 배너만 안 나오는 빌드는 알려진 .bin 중 없음(전부 배너 있음 또는 BOOT1 있음) |
- **결론**: 원인은 **미확정**. 가장 가능성 높은 것은 "배너가 나간 시점에 호스트가 포트를 읽고 있지 않았음"(H1+H2) [가설]. 확인하려면 **읽기 프로세스를 먼저 띄운 뒤** 리셋을 눌러 재캡처해야 하며, 이번 S9 에서는 금지라 하지 않음.

## 3. 10/16 주행 로그에 RESET CAUSE 가 없는 것 = "워치독 리셋 없음"의 증거인가?
| 로그 | RESET CAUSE/BOOT | 로그 시작 시점 | 리셋 흔적 |
|---|---|---|---|
| 141541 | 없음 | 첫 RADSTAT `t=749999 ms`, IMU bytes 2,464,263 → **부팅 후 약 12.5분 뒤부터 기록** | RADSTAT `t` 역행 0, IMU bytes 역행 0 |
| 151202 | `RESET CAUSE: other/pin`, BOOT1/BOOT2 1회 | 첫 `t=44977` | `t` 역행 1회(491080→7976) = 리셋 1회, **원인 other/pin (IWDG 아님)** |
| 152211 | 없음 | 첫 `t=157988` | `t` 역행 0. IMU bytes 역행 1회(505000→50566)는 숫자 한 자리 유실 줄(손상), 리셋 아님 |
- "RESET CAUSE 줄이 없다" **만으로는 증거가 되지 않음**: (a) 로그가 부팅 이후부터 시작하므로 그 이전 리셋은 안 보임, (b) 위 캡처처럼 배너가 유실될 수 있음.
- 대신 **`RADSTAT t=`(STM32 가동시간) 단조 증가 + IMU 바이트 카운터 단조 증가**는 리셋이 없었다는 직접 증거: 141541 은 1,601 s(t 749,999→2,351,628 ms) 동안 역행 없음, 152211 도 없음. 151202 의 리셋 1건은 `other/pin`(IWDG 아님).
- **슬라이드 13 문구 제안**: "RESET CAUSE 로그 없음" 대신 "가동시간 카운터가 로그 전 구간에서 단조 증가(141541: 1,601 s, 152211: 430 s 동안 리셋 0회); 151202 의 리셋 1회는 IWDG 가 아닌 other/pin". 단 **10/16 보드는 v17 이하**이고(배너 없음) 현재 보드(v18c 추정)와 다름 → 현재 펌웨어의 안정성으로 일반화하지 말 것.
