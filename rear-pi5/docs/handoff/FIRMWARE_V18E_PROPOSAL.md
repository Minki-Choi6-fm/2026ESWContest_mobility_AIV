# FIRMWARE_V18E_PROPOSAL — 차량 클래스 필터를 켜는 안 (문서만. 적용·빌드·플래시 금지)

기준: **v18c → v18d(txdrop 출력 한 줄, `main_v18d_proposed.c`) 다음 단계**. v18d 는 v18c 와 3곳(extern, RADSTAT 포맷, 인자)만 다르고 `TEST_ALL_CLASSES` 는 그대로 1 입니다(diff 로 재확인). v18e 는 그 위에서 **정확히 한 줄**만 바꾸는 별도 제안입니다.
`firmware/stm32_rear/main_v18c.c` 66행: `#define TEST_ALL_CLASSES 1`  →  **`#define TEST_ALL_CLASSES 0`**   (코드 622행 `if (!TEST_ALL_CLASSES && objClass != 1)` 가 비차량 객체를 건너뜀)
소스 파일은 만들지 않았습니다(승인 전).

## 왜 필요한가 (측정, 10/16 주행 로그 3개의 RADSTAT)
| 항목 | 141541 | 151202 | 152211 |
|---|---|---|---|
| UART 로 발행한 0x12 (`pub`) | 291,018 | 135,356 | 97,852 |
| 그중 차량 클래스 (`veh`, 필터 전 카운트) | 61,602 (21 %) | 48,579 (36 %) | 27,032 (28 %) |
| 선로 용량(≈527 0x12/s) 초과 초 | 2.9 % | 3.7 % | 3.5 % |
| 0x12 손실 중 그 초들의 몫 | 67 % | 70 % | 84 % |
| 객체 ≥500/s 초의 MCP2515 RX 넘침 | 222/223 | 93/95 | 51/51 |
→ 필터를 켜면 UART 0x12 부하가 **약 1/3–1/5** (평균 0.9–1.5 kB/s 수준)로 줄어 **선로 과부하 초가 사라질** 것으로 추정(차량 클래스 객체의 RCS 필터 통과 수는 `veh` 보다 작을 수 있음). CAN 입력(MCP2515) 부하는 줄지 않으므로 CAN 쪽 넘침은 별도 문제로 남음 [가설].

## 장점
- 변경 한 줄, 로직·타이밍·프로토콜 불변. 선로 부하와 TX 링 드롭을 가장 크게 줄임(→ 0x10/0x11/0x13 손실도 감소 기대).
- 가드레일/기둥/펜스 같은 점형체가 Pi5 의 타깃 후보에서 사라져 **가짜 후보와 "cut-in/정지 물체" 억제 사례가 줄 것**(재생에서 위험·주의의 대부분이 지면 고정 물체였음).

## 단점/위험
- **레이더의 차량 분류(objClass)에 완전히 의존**: 분류가 틀리면 실제 차량(특히 먼 거리, 정지 차량, 트럭 옆면)이 사라질 수 있음 [가설 — 분류 정확도는 측정한 적 없음].
- 점형체(사람·자전거·기둥)가 Pi5 에 전혀 안 보임 → 장래에 보행자/이륜차를 다루려면 다시 켜야 함.
- `objClass` 가 UART 로 전송되지 않아(CYCLE_INFO=0xFF) **지금은 Pi5 로 분류 정확도를 사후 평가할 수 없음**.
- 비교 없이 켜면 "왜 타깃이 사라졌는지" 구분이 안 됨 → 아래 비교 주행 필요.

## 켜기 전에 데이터를 얻는 방법 (선택, 별도 승인)
- **v18e-0 (진단용, 권장 선행):** 필터는 그대로 **끈 채**(`TEST_ALL_CLASSES 1`) 0x12 의 미사용 바이트(`p[13]`, 현재 `0xFF`)에 **`objClass`(0–3)와 필요하면 `dyn`/`class` 를 넣어 보냄**(프로토콜 v0.2 의 CYCLE_INFO 사용 방식 변경이므로 팀 합의 필요). 한 번 주행하면 Pi5 로그에서 "카메라(YOLO)와 매칭된 진짜 차량 중 레이더가 class 1 로 분류한 비율"(= 필터를 켰을 때의 **재현율**)을 계산할 수 있음.
- 이후 재현율이 충분하면 v18e 로 `TEST_ALL_CLASSES 0`.

## 비교 주행 방법 (v18d vs v18e, 같은 조건)
1. 같은 경로·같은 속도 구간을 두 번 달림: ① v18d(필터 OFF, txdrop 출력) ② v18e(필터 ON). 가능하면 같은 시간대/교통량. 매번 `live_receiver`/`pipeline_main --record` + `drive_logger_nouart`(영상, `stm_debug.log`) 로 기록(`CAR_TEST_RUNBOOK.md`).
2. 비교 지표 (모두 기존 도구로 계산):
   - 선로/큐: RADSTAT `pub`/초, 용량(≈527) 초과 초 비율, **`txdrop` 초당 증가량**, `loss_pct`(0x10/0x11) — `tx_queue_analysis.py`, `loss_analysis.py --txdrop`.
   - CAN 입력: `exp` 대비 `b`, `ovf` 증가 초 비율 — `log_evidence.py`.
   - 탐지 품질: 영상 구간에서 **YOLO 가 잡은 앞차가 레이더 객체로도 보이는 비율**(`lead_replay.py` 의 camera_confirmed, 같은 10초 구간 여러 곳), 앞차 거리 연속성(타깃이 사라지는 횟수/hold 발생 빈도).
   - 경고: 같은 장면의 위험/주의 비율과 "남은 위험(2)" 사례(`s4_replay.py`).
3. 판단 기준 제안 [PROPOSAL]: v18e 에서 (a) txdrop·손실이 의미 있게 줄고 (b) camera_confirmed 비율과 앞차 검출 연속성이 떨어지지 않으면 채택. 하나라도 나빠지면 v18d 유지 + 사이클당 객체 수 제한(옵션 3) 또는 보레이트 상향(옵션 5) 검토.
4. 플래시/리셋은 사용자와 팀이 결정. 업로드할 때마다 `~/flash_log.txt` 에 명령과 sha256 기록(`FIRMWARE_ON_BOARD.md`).
