# FIRMWARE v18d2 제안 (레이더 타임아웃 1000 ms + txdrop 표시) — 적용·빌드·플래시 안 함

STM32 담당 최민기님 결정: 레이더 타임아웃을 100 ms → 1000 ms. 이 문서는 **제안(diff)만** 담습니다. 빌드·플래시·보드 접속 없음.

## 1. 이유 (측정값)
| 사실 | 값 | 출처 |
|---|---|---|
| 책상(10/25), 물체 없음: 레이더 0x60A 상태 프레임 | 3~6/s, 간격 ≈305~310 ms, 최대 534 ms | 사용자 측정 |
| 물체 있음 | ≥15/s (≈60 ms) | 사용자 측정 |
| 현 펌웨어 타임아웃 | 100 ms → 앞이 비면 Safe Mode 진입 ≈3.4회/s (tec/rec 0, CAN 오류 없음) | 사용자 측정 |
| 10/16 141541 로그 | 1601 s 중 Safe Mode 진입 754회. `b=0`(물체 0) 초의 90.5 %에서 진입, 진입의 74 %가 b=0 초 | `radstat_safe_analysis.py` |
| 10/16 151202, 152211 | 모든 초에서 b>0, 진입 0, 초당 최대 간격 p99 85 / 67 ms | 동일 |
- 원인 해석("앞이 비면 레이더가 상태 프레임만 느리게 보냄")은 **[가설]**. 로그와 책상 측정이 일치하지만 레이더 사양서로 확인한 것은 아님.
- 1000 ms로 바꾸면 141541 의 진입은 **754 → 29회**(간격>1000 ms인 초 수). 임계별 남는 진입: 300 ms→244, 400→187, 534→90, 600→87, 800→33, 1000→29, 1500→16, 2000→5.
- 남는 29회 중 23회는 빈 장면 초(상태 프레임까지 1 s 넘게 끊김, 22초는 CAN 프레임 0개), 5회는 물체가 있던 초 → **"앞이 비어서"로 설명되지 않음**. 전원/CAN 끊김 후보는 별도 조사 필요.

## 2. 변경 (main_v18c.c 대비, 딱 두 가지)
파일: `firmware/stm32_rear/main_v18d2_proposed.c`, `main_v18c_to_v18d2.diff` (추가 7줄/삭제 4줄)
1. `tx_drop_count` 를 RADSTAT 에 `txdrop=` 로 출력 (v18d 제안과 동일 3줄).
2. `#define RADAR_TIMEOUT_MS 1000` 추가, `HAL_GetTick() - last_radar_rx_ms > RADAR_TIMEOUT_MS` (기존 `> 100`). 관련 주석 2곳 갱신.
- 배너 문자열은 **그대로 `FW v18c ...`** (바꾸면 펌웨어 구분이 쉬워지나 별도 선택사항: 지금은 diff 최소화 우선).
- sha256 앞 16자: v18c `11c720968228dc50` → v18d2 제안 `8c81789a6ca57b3e`.
- 확인: `100` 이 레이더 타임아웃으로 쓰인 곳은 **671행 한 곳**(+주석 2곳). 나머지 100 은 무관(dbg_tx 미사용 인자, SPI HAL 타임아웃, 하트비트 주기, BRAKE_ON_MG, SENSOR_TIMEOUT_MS). IWDG(PR=0, RLR=319 ≈40 ms), OBD 500 ms, 하트비트 **미변경**.
- 호스트 gcc `-fsyntax-only -Wall -Wformat`: v18c 와 오류·경고 동일(ARM 빌드 아님, arm-none-eabi-gcc 없음 → **실제 빌드 미검증**).

## 3. 필수 확인: 1000 ms 에서 마지막 물체가 "신선"하게 계속 나가는가?
- **아니오.** `radar_publish()` 는 0x60B 프레임 처리 때만 호출되는 이벤트 방식이고, 오래된 물체를 재전송하지 않음.
- 0x10 의 타깃 선택은 `radar_tbl` 항목을 **SENSOR_TIMEOUT_MS(100 ms) 이내**만 사용 → 물체 유효시간은 **별도 상수**이며 이번 diff 에서 **변경 없음**. OLED 의 "마지막 물체" 표시(1000 ms)도 별개.
- 따라서 타임아웃을 1000 ms 로 해도 100 ms 지난 물체는 0x10 타깃에서 빠진다(오래된 물체를 1 s 동안 내보내지 않음). 별도 수정 필요 없음 → diff 에 포함하지 않음.

## 4. 위험
- **진짜 레이더가 죽어도 최대 ≈1 s 늦게 감지**: 그동안 RADAR_OK=1, SAFE_MODE=0, 0x10 은 "타깃 없음". Pi5 는 `radar_alive` True + 타깃 없음 → **level 0("타깃 없음(레이더 정상)")**, 기존에는 0xFF("?"). 즉 최대 1 s 동안 앞차 위험을 못 보는데 "정상"으로 보임. 부저는 level 2 에서만 울리므로 오경보 쪽 위험은 없고, **누락 쪽** 위험.
- 반대로 이득: 빈 장면에서 level 0xFF 깜박임(141541: 레벨 변화 1693회 중 89 %가 Safe 토글 때문, 0xFF 구간 753회/225 s), BSM 의 SAFE_MODE/SENSOR_DEGRADED 깜박임이 사라짐. 추적(target_select)·K 추정(k_estimator)은 Safe Mode 를 참조하지 않아 깜박임으로 초기화되지는 않았음(코드 확인). `DangerState` 만 0xFF 에서 리셋됨.
- 안전 상수 변경이므로 RULES.md 규칙 5/8(100 ms 기준, 안전 상수는 코드 리뷰) 예외에 해당 → **리뷰 기록 필요**.
- Pi5 쪽 충돌 확인: SAFE_MODE(bit4)/RADAR_OK(bit0) 를 읽는 곳은 `brain.py`→`danger.py` 와 `bsm_builder.py` 뿐, `TIMEOUT_MS['radar']=100`(0x12 도착)과 `radar_alive`(0x10 bit0)는 의미 충돌 없음. 단 `fake_stm32` "dead" 모드는 비트를 즉시 바꿈(실제 펌웨어는 최대 1 s 지연).
- 선택 대안(미적용): 프로토콜에 "마지막 레이더 프레임 경과시간" 필드 추가 — v18d2 범위 아님.

## 5. 적용 전 체크리스트
1. `sha256sum main_v18d2_proposed.c` 가 `8c81789a6ca57b3e…` 인지 확인, 값을 `~/flash_log.txt` 에 기록(파일명, 날짜, sha256, 플래시 명령).
2. 규칙 5/8 리뷰(위험 §4) 기록. 사용자가 CubeIDE `main.c` 에 diff 적용(`main_v18c.c` 와 바이트 동일 확인 후).
3. 플래시 전 현재 보드 .bin 백업 여부 확인(가능하면). 차에 싣기 전 책상 검증.

## 6. 적용 후 확인 (책상)
- 빈 장면에서 RADSTAT `safe=` 값이 **증가를 멈춤**(기존 ≈3.4/s), `RADAR TIMEOUT` 로그 없음.
- 레이더 CAN/전원을 뽑으면 약 1 s 뒤 `RADAR TIMEOUT -> SAFE MODE` 가 나옴.
- RADSTAT 에 `txdrop=` 가 보임(0 이 정상). 물체 있을 때 `b`, `exp` 가 이전과 같은 수준.
- 배너가 계속 `FW v18c` 이므로 구분은 sha256 기록 + `txdrop=` 필드 유무로 함.

## 7. 최종판 안내 (S10)
사용자 결정("추천대로")에 따라 배너 재출력과 배너 문자열 `FW v18d2 (…)` 를 합친 **최종 제안**은 `firmware/stm32_rear/main_v18d2_final_proposed.c` / `main_v18c_to_v18d2_final.diff` 입니다(이 문서의 S9 파일은 그대로). 플래시 절차: `FLASH_PROCEDURE_V18D2.md`. 이 문서 §2 의 "배너는 v18c 그대로"는 최종판에서 바뀝니다.
